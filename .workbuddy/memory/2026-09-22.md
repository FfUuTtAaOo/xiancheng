## 可复用的命令行构建方式

STM32 VS Code 扩展的 `cube-cmake` 依赖 `cube` 命令与 CUBE_BUNDLE_PATH，脱离 VS Code 直接调用需补齐环境：

```bash
BUNDLE="/c/Users/y3010/AppData/Local/stm32cube/bundles"
CORE="/c/Users/y3010/.vscode/extensions/stmicroelectronics.stm32cube-ide-core-1.4.0-win32-x64/resources/binaries/win32/x86_64"
BCMAKE="/c/Users/y3010/.vscode/extensions/stmicroelectronics.stm32cube-ide-build-cmake-1.46.0-win32-x64/resources/cube-cmake/win32/x86_64"
export PATH="$CORE:$BCMAKE:$BUNDLE/gnu-tools-for-stm32/14.3.1+st.2/bin:$BUNDLE/ninja/1.13.2+st.1/bin:$PATH"
export CUBE_BUNDLE_PATH="C:/Users/y3010/AppData/Local/stm32cube/bundles"

"$BCMAKE/cube-cmake.exe" -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_TOOLCHAIN_FILE=D:/ST/workspace/vscode/xiancheng/cmake/gcc-arm-none-eabi.cmake \
  -DCMAKE_COMMAND=cube-cmake -DCMAKE_EXPORT_COMPILE_COMMANDS:BOOL=TRUE \
  -S D:/ST/workspace/vscode/xiancheng -B D:/ST/workspace/vscode/xiancheng/build/Debug -G Ninja

"$BCMAKE/cube-cmake.exe" --build D:/ST/workspace/vscode/xiancheng/build/Debug
```

## 新增功能：4-20mA 输出映射（N值 → Modbus RTU）

**需求**：原来上位机发 `02` 后一直发 `AA 55 02 [6×float] 0D 0A` 连续数据流。现改为按检测值映射成 4-20mA，通过 Modbus RTU 指令下发给毫安输出模块。

**值映射规则**（已用独立脚本逐例验证通过）：
- 用户设「零值 Z」和「极值 E」，**另一端极值 = Z − E**（三个例子都吻合：Z=1/E=10→−9；Z=1/E=−10→11；Z=0/E=0.3→−0.3）
- 端点 hi = max(E, Z−E)，lo = min(E, Z−E)
- N ≥ Z：`12 + 8×(N−Z)/(hi−Z)` → 12~20mA，超端点钳位
- N < Z：`12 − 8×(Z−N)/(Z−lo)` → 4~12mA，超端点钳位
- 寄存器原始值 = mA × 1000（从站默认小数点 3 位）。N=1/Z=0/E=8 → 13mA → 13000 → `32 C8` ✓

**Modbus 帧**（21 字节，一帧下发全部 6 路）：
`01 10 00 0A 00 06 0C [ch1..ch6 各2字节大端] CRC_L CRC_H`
- CRC16-Modbus（poly 0xA001，初值 0xFFFF），低字节在前。已用标准向量 `01 03 00 00 00 01 → 84 0A` 验证
- 示例（ch1=13mA，其余=12mA）：`01 10 00 0A 00 06 0C 32 C8 2E E0 2E E0 2E E0 2E E0 2E E0 BB FB`

**新增文件**：`Core/Inc/ma_output.h`、`Core/Src/ma_output.c`
**改动**：`rs485_cmd.h/.c`（新命令）、`rs485.h/.c`（`rs485_send_plain`）、`sensor_types.h`（`g_sys.output_mode`）、`main.c`（init + 20ms 轮询 + LED 心跳条件）、`CMakeLists.txt`

**新增 RS485 命令**：
| 命令 | 格式 | 作用 |
|---|---|---|
| 0x50 | `AA 55 50 [ch 1..6] [float32 大端] 0D 0A` | 设通道零值（12mA 锚点） |
| 0x51 | `AA 55 51 [ch 1..6] [float32 大端] 0D 0A` | 设通道极值 |
| 0x52 | `AA 55 52 [0\|1] 0D 0A` | 输出模式：0=AA55数据帧，1=Modbus mA |
| 0x53 | `AA 55 53 0D 0A` | 查询 6 通道零值/极值，回 48 字节 |

**关键决策**（用户确认）：复用 USART1 同一总线；一帧含 6 路通道值（从站固定 01）；20ms 一轮（50Hz）；两种输出模式并存可切换。

**EEPROM 新增占用**（AT24C04）：`0x80–0xAF` 48字节配置、`0xB0` 有效标志 0x5A、`0xB1` 输出模式。原有：`0x78–0x7B` 波特率、`0x7C` 数据格式。

**编译**：RAM 7792B/20KB (38.05%)，FLASH 46884B/128KB (35.77%)，无新增警告。

**遗留待确认**：0x50/0x51 用的是 **float32 大端**（按 `3F 80 00 00`=1.0 推断），而现有 0x20 矩阵上传用的是小端 —— 若上位机统一用小端需调整。

## 追加：mA 配置出厂默认 + 修正 EEPROM 地址冲突

**需求**：开机从 EEPROM 读零值/极值；读到**全 0xFF**（空白）时用默认值 —— 零值 0，通道 1/2/3 极值 0.3，通道 4/5/6 极值 0.03。

**改法**：
- `ma_output.h` 新增 `MA_DEFAULT_ZERO/EXTREME_A/EXTREME_B/SPLIT_CH` 四个宏。
- `ma_output.c` 新增 `ma_output_apply_defaults()`、`f32_is_valid()`、`buf_is_blank()` 三个静态函数。
- `ma_output_init()` 改为「先铺默认 → 再由 EEPROM 覆盖」，空白/非法即保留默认。
- `ma_output_load()` 改为**先读 48 字节配置块判断全 0xFF**（不再只看 magic 字节），再做整体 float 合法性校验（NaN/Inf/超 1e9 全部拒收），最后才落盘到 RAM——避免半截非法数据污染运行配置。

**⚠️ 修正上一轮的错误地址分配**：上一轮我把 mA 配置放在 EEPROM `0x80–0xAF`，**与既有数据撞车**：
- `0x80–0x97` = 矩阵第 6 行（`flash_save_matrix` 硬编码 0x80）
- `0x98–0xAF` = 零位标定 `force_zero[6]`（`FLASH_OFF_ZERO=0x98`）
- 现改为 `0xC8–0xF7` 配置 / `0xF8` 有效标志 / `0xF9` 输出模式，全部落在唯一映射的空闲区。
- 已把完整 EEPROM 布局表写进 `ma_output.h` 注释与项目 MEMORY.md，避免再撞。

**验证**：
- 编译通过，无警告。RAM 7792B/20KB (38.05%)，FLASH 47180B/128KB (36.00%)。
- 独立脚本复核默认映射：ch1-3 N=0.3/0.15/0/−0.3 → 20/16/12/4mA；ch4-6 N=0.03/0.015/0/−0.03 → 20/16/12/4mA，超端点正确钳位。
